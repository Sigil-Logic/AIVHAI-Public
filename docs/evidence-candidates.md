# Candidate Assurance-Case Evidence

**Status**: Living document  
**Version**: 0.2.1  
**Date**: 2026-10-10  
**Project**: AIVHAI  
**Issue**: [#176](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/176)  

---

This document lists existing artifacts that **could** become evidence in AIVHAI's assurance case, and records what each could and could not support.  Nothing in it is evidence yet.  A candidate becomes evidence when it runs against pinned artifacts, produces a dated record under `.evidence/`, and is cited by the claim it supports.

The assurance case is multi-dimensional: proof, validation, and runtime verification and testing ([#51](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/51)).  How the project validates is being decided in [#168](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/168), which requires validation and verification to be reported separately.  This register exists so that test suites already sitting in the corpus are not forgotten when that practice is set.

## The CHERIoT test suites

Murali Vijayaraghavan (Cherified) named both suites on [#176](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/176) on 2026-10-05, as what he tests the Guru-based `cheriot` core with.  Both suites and the compiler that builds them are pinned in [AIVHAI-Everything](https://github.com/Sigil-Logic/AIVHAI-Everything) as upstreams, not forks:

| Suite                                                                                             | Pin        | What it exercises                                                                                                                                                                                                                                   |
|---------------------------------------------------------------------------------------------------|------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| [`OpenSeCura/basic-riscv-tests-cheriot`](https://github.com/OpenSeCura/basic-riscv-tests-cheriot) | `d028d7cb` | 42 per-instruction tests in the `riscv-tests` style, signalling through `tohost`: integer arithmetic, branches, and the CHERIoT-specific forms of jumps, loads, stores and `auipc`.  `cheriot`'s `run_all_tests.sh` runs each on the simulated core |
| [`CHERIoT-Platform/cheriot-rtos`](https://github.com/CHERIoT-Platform/cheriot-rtos) `tests/`      | `17ae734b` | The RTOS's own suite: compartment calls, static sealing, stack integrity, crash recovery, the allocator, futexes, queues, and thread pools                                                                                                          |

Both are compiled by CHERIoT LLVM, pinned at `b62de6f4`.  See [`tools.md`](tools.md) for that compiler and why it is pinned.

### What they could support

1. **Validation of the Guru toolchain leg.**  The core under test is generated by Guru from a Rocq specification.  Running an independently written ISA suite and an RTOS suite on the simulated core and on its generated RTL is evidence that the Guru flow produces hardware that runs real CHERIoT software.  That bears on the Guru leg of the datapath proof, since the same toolchain is what AIVHAI uses there.
2. **Scenario sources for the compartmentalisation firmware (CF).**  The RTOS suite exercises the same mechanisms that the 64-bit CF must provide: cross-compartment calls, sealing, and stack and crash isolation.  The 32-bit CHERIoT model is also what the CF work extends to 64 bits ([#52](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/52)).  These tests are candidate **requirement scenarios** for the CF, to be refined into CF tests under [#168](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/168).
3. **A differential cross-check.**  The same ELF can run on the Guru core and on the CHERIoT Sail emulator.  Disagreement between the two would locate a spec or implementation divergence.  This requires `CHERIoT-Platform/cheriot-sail`, which is not pinned; [#54](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/54) owns that decision.

### What they cannot support

- **They are tests, not proofs.**  A passing suite is validation evidence over the cases it runs.  It does not discharge any property, and it is reported apart from verification results.
- **They test CHERIoT, not AIVHAI's targets.**  CHERIoT is a 32-bit RV32E platform with its own capability encoding.  It is not RVY, CVA6-CHERI, or the Coral NPU.  Using a CHERIoT result as evidence about an AIVHAI target requires porting the test and justifying the transfer, and that justification is a claim in its own right.
- **The Guru core's ISA deliberately differs from `cheriot-sail`.**  `cheriot`'s README lists the differences, including deferred jump faults, `MePrevPcc`, and a 5-bit exponent encoding.  A test passing on the Guru core is therefore evidence against Murali's specification, not against mainline CHERIoT.
- **No coverage claim follows.**  Per [#168](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/168), a coverage claim must name what is covered and by what.  Neither suite has been measured against either core.
- **Nothing here addresses side channels or physical attack**, which are outside the formal boundary in any case (SL-AIVHAI-P04).

### Provenance: why the compiler is pinned

The binaries are built, not shipped, so any result is a result about a binary that a specific compiler produced.  `cheriot`'s `Makefile` compiles `simple.elf` into `Binary.v`, which is the initial memory of the instantiated specification and implementation (`SpecInst.v`, `Impl/ImplInst.v`).  No theorem depends on it, but the Rocq build cannot complete without it.  A test record must therefore name four commits: the core, the suite, CHERIoT LLVM, and Guru.

### What is still missing

- **A CHERIoT LLVM build of `b62de6f4`.**  No AIVHAI image carries one, so neither suite can be built from the pins yet.  [`tools/rocq-foundations.md`](tools/rocq-foundations.md) reports the `cheriot` core as NOT BUILT for this reason.
- **The RTOS's build system**, `xmake`, and a decision on whether the RTOS suite runs on the Guru core, on the Sail emulator, or on both.
- **A home in Continuous Verification** ([#154](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/154)), once the validation practice says what these runs are for.

## The CHERIoT program logic

[`cheriot-program-logic`](https://github.com/Sigil-Logic/cheriot-program-logic) is pinned again at `6bc57624` by [AIVHAI-Everything#7](https://github.com/Sigil-Logic/AIVHAI-Everything/pull/7), reversing the 2026-10-04 drop, under the Decision of 2026-10-10 on [#176](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/176).  It is a work-in-progress ISA-level program logic for CHERIoT (Google, Apache-2.0, derived from ZeroRisc's `otbn-model`): about 3,400 lines of Rocq 9.0 giving a functional model of about fifty CHERIoT instructions (`src/ISA.v`), a weakest-precondition semantics and separation logic over tagged memory (`src/Semantics.v`), proof automation, and three worked examples.  The third example verifies a subset of the `cheriot-rtos` switcher's context-restore path, cited by line to `sdk/core/switcher/entry.S`.  Upstream has not moved since 2026-06-11.  It is held as a pin, not built: the build track is deferred to [#247](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/247).

### What it could support

1. **The firmware goal G-CF** ([#226](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/226)).  The abstract specification's proved theorem, `ThreadIsolatedMonotonicity`, covers same-domain traces only; compartment calls, returns and exceptions are excluded, and the `SwitcherProperty` contracts that would cover them are specification without proof ([#213](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/213)).  A program logic over the switcher's machine code is the kind of artifact that discharges such contracts.  This development is the only start on that bridge in the corpus.
2. **A method reference for binary-level firmware proofs in Rocq.**  Omnisemantics with coqutil's separation logic over a capability machine is a reusable shape for the 64-bit compartmentalisation firmware, whatever the final ISA model is.

### What it cannot support

- **Nothing in it is evidence today.**  Seven ISA definitions are `Admitted` opaque functions (`getTagAddr`, `isCapAligned`, `lastTwoBitsZeroed`, `lastBitZeroed`, and the three `mstatus` helpers), four `Zmod` lemmas are `Admitted`, and two axioms (`TODO`, `PP`) exist, though both are trivially inhabited.  Memory is a hard-coded 8 KiB.  There is no exception-delivery or trap semantics (exception conditions on loads, stores, `cret`, `mret` and `cspecialrw` are detected, then routed to a `TODO`), no interrupts and no PCC check on fetch.  The README's own "contributing" list is the gap list.
- **It is 32-bit CHERIoT, not RVY.**  `XLEN` is fixed at 32 and `word32` is pervasive; only the capability encoding is abstracted, behind the `Ecap.ecap` class.  Any use for AIVHAI's 64-bit targets is a transfer claim in its own right (SL-AIVHAI-P04), as for the abstract specification.
- **It shares no definitions with the abstract specification.**  The abstract specification assumes per-instruction behaviour through `WfNormalInst`; the program logic defines its own ISA.  Connecting the two is a project, not a lemma.
- **Nothing in it bears on G-a or G-c/d/e.**  Murali Vijayaraghavan's assessment that it is *"not very useful for RVY"* ([#176](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/176), 2026-10-04) stands for the ISA and microarchitecture goals.

### Provenance

Google copyright 2026, Apache-2.0, with a Google CLA on contributions.  The 2026-10-04 Decision on [#176](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/176) narrowed AIVHAI's declared background IP by dropping it; the 2026-10-10 Decision widens it again, for the reason above, and says so.
