This directory holds AIVHAI's project-level assurance artifacts: the threat model, the structured assurance case, and the census of properties established by earlier work.  This README says how they fit together, and how the project intends to assure every property it has identified, both the properties inherited from earlier CHERI and RISC-V work and the new ones it derives as the design is refined.

**Everything here is a first draft, and none of it has been vetted in depth.**  The threat model, the case and the census were written in week five of the project.  They were largely generated by Sigil Logic's HOARDE agents and have had only light review; the AIVHAI team has not yet vetted them in depth.  Feedback from the red team is very welcome, read with that in mind.  Nothing in this directory reports an AIVHAI result: every goal of the case is still an obligation.

## 1. The NINJA view: a property lives in the refinement chain

AIVHAI is engineered with NINJA, Sigil Logic's rigorous digital engineering methodology.  Its central discipline is that every artifact is traceable both to what it refines and to what refines it, along one chain:

```
  domain model  ->  requirements  ->  architecture  ->  design  ->  implementation  ->  evidence
                         |                                  |               |
                    a property is                      and refined     and codified in it:
                    refined FROM a                     TO a design,    contracts, inline
                    requirement ...                    as a contract   assertions, test benches,
                                                                       verification benches
```

**A property is never free-standing.**  It is refined *from* a requirement, and *to* a design, where it is codified in whichever form the artifact at that level admits:

| Level and artifact                                                | How a property is codified there                                                                                                                                                                                       |
|-------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ISA: the RVY Sail model                                           | Model-level preconditions and postconditions as explicit assertions; properties over the model stated as theorems (the RVY properties RP1 to RP5) and, per function, as SMT properties                                 |
| Microarchitecture: CVA6-CHERI in SystemVerilog, the Guru datapath | SystemVerilog Assertions in the RTL and its verification benches; refinement of the Sail model as the correctness statement; in Guru, the atomic functional specification a pipelined implementation is proved against |
| Firmware: the compartmentalisation firmware                       | Its informal specification's core rules as invariants; a Rocq model whose theorems state them; contracts at every entry, return and trap; runtime assertions in the prototypes                                         |
| Every level                                                       | Test benches that execute the property, traced to the requirement scenario that motivates them                                                                                                                         |

**A property is then checked twice over: dynamically and statically.**  Dynamically, by executing the artifact: running a model, simulating RTL, running firmware, and evaluating the property's codified form on every run.  Statically, by reasoning about all executions at once: model checking, automatic theorem proving, and interactive theorem proving.  The two are complementary.  A proof covers every input of a model, and an execution covers what the proof's model leaves out, ultimately the hardware as built.  Each kind of evidence is reported for what it is, and validation is reported apart from verification ([#168](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/168)).

## 2. Where the properties come from

The case argues about four sources of property, and every property it carries says which one it came from.

1. **The record of earlier work.**  [`property-provenance.md`](property-provenance.md) reads what has been stated, tested, checked or proved for CHERI and RISC-V designs, property by property, and condenses it into a canonical set, CAN-01 to CAN-18, each with its first statement and its strongest result.  These are inherited properties: AIVHAI must establish each of them anew for its own design, and the census says what that obligation is.
2. **The threat model.**  [`threat-model.md`](threat-model.md) states, for each threat, the goal of the case that is to counter it.  A threat with no precedent in the record yields a new property: tenant state across compartment switches (goal G-CF7) arose this way.
3. **The requirements.**  `AIVHAI-SYS-R01` to `R12` trace to the commitments in the proposal's Table A.  Each goal of the case names the requirement it discharges, or the requirement it is part of.
4. **Properties derived through the method.**  Refinement produces properties no source states: an informal property becomes a precise one when its level's artifact must express it (RP1 to RP5 are the Sail-level form of one requirement), and a finding produces one when it is understood.  The two RVY Sail model defects of 2026-10-11, found by a Rocq proof over the model, yielded threat TM-049 and sharpened RP4 and RP5 ([`../../docs/red-team/sprint-1/isa-issues-2026-10-11.md`](../../docs/red-team/sprint-1/isa-issues-2026-10-11.md)).  New properties are added to the census's map, the threat model and the case together, and the cross-checks below keep the three consistent.

## 3. How each property will be checked: the whole spectrum

ARIA's programme is focused on assurance cases grounded in formal verification, and this project's deliverable is a series of machine-checked proofs.  Applied formal methods, however, is a broad spectrum.  It runs from executable specifications and model-based testing, through runtime verification, to model checking and automatic and interactive theorem proving, and AIVHAI intends to bring all of it to bear on this SoC.  The reason is the same as in our earlier high-assurance work: each technique covers what another cannot, and a property that is both proved over a model and observed to hold on every execution of the hardware is better assured than one checked only one way.

| Technique                                  | Static or dynamic | Where it applies in AIVHAI                                                                                                                                                                | Status today                                                                                  |
|--------------------------------------------|-------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| Executable formal models                   | Dynamic           | The Sail model compiled to its C emulator, which runs firmware and test programs; Capabilities Limited's compartment firmware runs on it                                                  | In place; CI checks the model builds                                                          |
| Differential and tandem testing            | Dynamic           | The Sail model as the golden reference against CVA6-CHERI (TestRIG); a first differential test of the RVY model is [#126](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/126)         | Planned; the 2026-10-11 defects show why the reference itself must be checked (threat TM-050) |
| Test benches and scenario tests            | Dynamic           | Requirement scenarios as executable tests on the models; the CHERIoT test suites as candidate scenario sources ([`../../docs/evidence-candidates.md`](../../docs/evidence-candidates.md)) | Planned                                                                                       |
| Inline assertions and runtime verification | Dynamic           | Sail model assertions; SystemVerilog Assertions in RTL simulation; contracts checked at runtime in firmware prototypes                                                                    | Planned, with the artifacts                                                                   |
| Red-teaming                                | Dynamic           | Trail of Bits, every sprint, against the models now and the hardware from about month 14                                                                                                  | Under way; Sprint 1 is a practice run                                                         |
| SMT checking of model properties           | Static            | Per-function properties of the Sail model and its capability encoding                                                                                                                     | Precedent in the record; planned for RVY                                                      |
| Model checking                             | Static            | SystemVerilog Assertions with Jasper, or the open Yosys and TabbyCAD flow, over CVA6-CHERI and the vector and matrix datapaths                                                            | Planned (goals G-c1 to G-c5)                                                                  |
| Automatic theorem proving                  | Static            | Equivalence and refinement checks between models and generated or hand-written components (the SAW and Cryptol leg of Sigil Logic's toolchain)                                            | Planned where a component admits it                                                           |
| Interactive theorem proving                | Static            | Capability monotonicity of the RVY Sail model (goal G-a1); the firmware's Rocq model and the proof of its implementation (G-CF2, G-CF3); the Guru refinement proofs (G-c3)                | Under way: the plan for G-a1, and Capabilities Limited's Rocq proof of the firmware prologue  |

Whatever the technique, a check becomes evidence in the same way.  It runs from pinned inputs in a pinned toolchain image, with the command that re-runs it written down beside it, and it is attached to the case under the checker's rules.  A test that passes is validation evidence over the cases it runs; a proof is verification evidence under the assumptions it states; and the case says which each piece of evidence is.

## 4. The lineage this practice comes from

The approach is not new to this project; AIVHAI follows practice proved on earlier high-assurance systems.

- **HARDENS** (Galois, 2022; [`GaloisInc/HARDENS`](https://github.com/GaloisInc/HARDENS)), a reactor trip system on a three-core RISC-V SoC, carried every property from requirement to binary.  Each requirement became a theorem about an executable Cryptol model, proved for all inputs where an automatic prover could, and randomly tested where it could not.  C and SystemVerilog components were generated from the model and proved equal to it with SAW.  C code was proved correct against the model, and free of runtime errors, with Frama-C.  Every high-level scenario became an integration or system test, generated from the model where possible, and run on every *rigorous digital twin* of the system: the software alone, the SoC simulated in Verilator, and the SoC on an FPGA.  Its assurance case gives two reasons that testing stays essential beside proof.  Some stakeholders trust execution more than proof.  And only execution exercises the real deployment hardware.
- **VoteSecure** (Free & Fair; [`FreeAndFair/VoteSecure`](https://github.com/FreeAndFair/VoteSecure)) gives the shape of the artifacts around the evidence.  It has a domain model, a feature model, a threat model, a formal protocol model and a SysML system model, all under rigorous digital engineering.  Its threat model is published both statically and as an interactive application, and its assurance case is a skeleton generated from the models.  AIVHAI follows the practice, not the tool: its case is plain GSN in JSON, checked in CI ([`../../docs/red-team/prior-engagements.md`](../../docs/red-team/prior-engagements.md)).
- **The DARPA SSITH programme and its FETT bug bounty** set the standard for what a red team is given: every design, the code, the tools, a way to inject software, and the location of the secrets.

AIVHAI's digital twins are, in order of arrival, the Sail model and its C emulator, the RTL in simulation, and, from about month 14, the SoC on an FPGA.  A property is checked on each twin its form allows, and the case records on which.

## 6. How the case is organised

The root goal is the proof series of [#1](https://github.com/Sigil-Logic/AIVHAI-Sigil/issues/1).  One strategy decomposes it by layer of the trusted computing base into four goals the threat model already names in its disposition column: **G-a** the ISA, **G-c** the microarchitecture, **G-CF** the compartmentalisation firmware, **G-comp** their composition.  Every goal that discharges a requirement of `specs/requirements/system.md` names it, with the Table A cell from that requirement's Source line; a goal that is a part of a requirement, or a precedent for one, says so.  The assumptions register A-1 to A-6 is the threat model's, in the same numbering.

**The worked examples are attached, not copied, and neither is evidence for an AIVHAI goal.**  The format has no module node.  A sub-case is attached as a `context` node, pinned to its JSON at a commit with the command that re-derives its rendering, of the goal it bears on: the RVY Sail plan beneath G-a1, which stays `undeveloped` because a plan is not evidence; the CHERIoT theorem beneath G-CF2, as the precedent its method rests on (J-CF2), and included in the release for pedagogy.  Artifacts that demonstrate without proving, such as Capabilities Limited's compartment firmware beneath G-CF4 and G-CF7, attach the same way, and so do the records of prior work: the census, one context node per layer (C-prov to C-prov-CF), Murali Vijayaraghavan's CHERIoT mechanisations at the goals each bears on (C-lin), and Capabilities Limited's write-up of the 2026-10-11 model defects (C-ISA1).  A sub-case becomes a `solution` only when it discharges an AIVHAI goal.

**The skeleton establishes no AIVHAI result yet.**  Every leaf goal is `undeveloped` with the reason given, and the case is `draft`.  Known gaps GAP-1 to GAP-9 of the threat model are `context` nodes of the same names, each attached to the goal it bears on.  `make ci`, `make release-check` and `release.yml` validate this directory beside `docs/red-team/assurance-case`, and `scripts/release/cut-release.sh` applies the strict `--release` mode and its pin check against the release's targets to both.

**Three documents, checked against one another.**  Every threat's disposition names the most specific goal of the case that is to counter it, and every threat a goal cites must name that goal or a sub-goal in return; `scripts/assurance/check-threat-model.py` enforces both directions, and threat model §10 lists its rules.  The census maps each of its rows to the case's goals, and `build-property-catalogue.py check` confirms that every catalogue row the census cites exists.

## 7. Checking

```bash
python3 scripts/release/check-assurance-case.py --render specs/assurance   # after editing the JSON
python3 scripts/release/check-assurance-case.py specs/assurance            # the gate, also run by make ci
python3 scripts/assurance/check-threat-model.py                             # the threat model against the case
python3 scripts/assurance/check-threat-model.py --selftest                  # its negative controls
python3 scripts/assurance/build-property-catalogue.py check specs/assurance/property-catalogue.jsonl specs/assurance/property-provenance.md
```

The case checker's rules are listed in [`docs/red-team/assurance-case/README.md`](../../docs/red-team/assurance-case/README.md).  No checker can tell whether a goal's prose matches the formal statement or requirement it cites; that is the reviewer's first question, and a mismatch is a finding.
